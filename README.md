# GTAV Mods Manager

[Visit the GTAV Mods Manager website](https://spacesquare640.github.io/GTAV_Mods_Manager/)

Code: PolyForm Noncommercial License · Website content: CC BY-NC-SA

GTAV Mods Manager is a source-available, non-commercial desktop app for installing, translating and managing GTA V mods. It is not affiliated with Rockstar Games or Take-Two Interactive.

Current development focuses on GTA V Legacy single-player and Legacy LSPDFR. GTA V Enhanced and FiveM (client, server tools, and conversion) are under development and blocked by the backend. Existing settings, mod records, and pending-mode recycle-bin snapshots are retained. The UI will be updated separately. OIV packages remain unsupported; use OpenIV to install them.

Overlaps with files tracked by another active mod require explicit confirmation, including when the overlap resembles an update. Reinstall checks the new package and known conflicts before uninstalling the old version, but later I/O or database failures may still require restoring the old version from the recycle bin.

Existing target files without a recorded active owner also require confirmation. The conflict report identifies their owner as unknown. A reinstall only exempts its own restored original when its content matches the backup recorded before uninstall; changed files and other active owners still require confirmation. Non-regular targets, including symbolic links, are rejected.

Reinstalling an active mod also requires every recorded old backup to remain available as a regular file, because uninstall processes the old version's complete file set. Reinstalling a disabled mod may require confirmation for original files already restored by disable; it does not exempt them as newly restored backups.

Active uninstall validates its targets and reads every recorded backup before changing files. Missing or unreadable backups stop the operation before snapshot creation; failures after these checks can still require recovery, so this is not a complete rollback guarantee.

Active uninstall rejects targets outside the supplied game root, unsafe relative paths, and existing ancestors that resolve outside that root. It also refuses any target tracked by another active mod. Because overwrite-chain ordering is not recorded, this conservative protection can block uninstalling either overlapping mod; it does not provide automatic conflict-chain removal. These preflight checks do not eliminate filesystem races or later I/O failures.

The app uses its own recycle-bin snapshot directory, never the operating system's recycle bin. Disabled uninstall snapshots verified staged payloads without modifying current game files, original backups, or shared DLC metadata. New disable operations record file identities and actual staged hashes, including user edits; older staging without a manifest must match its recorded file hashes or the operation stops for recovery. Staging and old backups are retained, so this can temporarily use additional storage. Restore uses the existing snapshot format and reactivates the mod; DLC registration is now deferred to durable manual reminders, while full transactional filesystem recovery remains incomplete. Core callers must use the staging-aware uninstall/reinstall APIs for disabled mods; old APIs reject missing context. App, CLI, and AI commands supply their existing staging root.

Rollback also reads its backup before removing the current target, to detect existing read locks early. These checks do not prevent files from changing afterward and do not provide atomic replacement.

Recycle-bin restore requires the associated mod to remain uninstalled and checks the complete restore target set for other active owners before creating backups or changing files. An ownership conflict preserves the entry for later recovery. Existing regular files without an active owner keep the existing backup-and-replace behavior; the app cannot prove whether they are originals or newly added external files.

Restore preflights absolute paths, safe relative components, resolved source/target ancestry, ordinary readable files, duplicate targets, and overlapping snapshot/target/backup storage. Every required backup completes before the first target write. Backup candidates use exclusive creation and the same open handle for copying, preserving existing files and partial recovery data on failure. These checks do not establish hard-link identity, prevent later directory replacement, or provide atomic target writes or complete filesystem/database rollback.

Restore requires an existing game-root directory and absolute game, snapshot, and backup roots; missing target subdirectories inside the game root can still be created. A dangling link in a backup candidate causes a conservative refusal instead of automatic collision retry.

After all target copies complete, restore commits every file hash and backup path, the mod status, restore event, and recycle-bin entry removal in one database transaction. SQL failure rolls back these metadata changes and leaves snapshots and new backups available for recovery. Target files may already contain restored payloads; this is database consistency protection, not filesystem rollback. Cleanup runs only after a successful commit.

App and CLI cleanup now supply their recycle, backup, and staging roots independently of database snapshot paths. A cleanup entry must be a direct child of the dedicated recycle root, with no linked/reparse ancestors or tree members, resolved-path workspace/storage overlaps, or other snapshot references. Unknown, missing, pending, active, or disabled owners and unverifiable snapshot directories are retained by expiry sweeping. CLI sweeping runs before commands; the App requests it from its tools effect, which may run repeatedly. There is no background scheduler.

Legacy core restore APIs still restore files and remove the restored entry, but retain its filesystem snapshot because they lack cleanup context; legacy `sweep_expired` returns zero without removing data. Call `restore_with_recycle_root` and `sweep_expired_with_root` with explicit storage roots for guarded cleanup. Retained snapshots or partial cleanup remnants can consume additional space and may need separately authorized recovery/cleanup. A post-commit cleanup failure logs the retained path without turning a successful restore into failure. Tree scanning and final revalidation do not establish hard-link or mount identity or eliminate concurrent path replacement; this is not a handle-based, race-free deletion guarantee.

Download installers only from [GitHub Releases](https://github.com/KingsleyHK0323/GTAV_Mods_Manager/releases) and verify the SHA-256 checksum file attached to each release. See [PRIVACY.md](PRIVACY.md) and [TERMS.md](TERMS.md).

Production ACL and recovery stop conditions remain in force even if these initial probes pass.

### Semi-automatic DLC registration: implementation awaiting validation

<!-- OpenAI-Codex -->
The source no longer automatically adds or removes DLC registration entries during installation, uninstallation, reinstallation, rollback, or recycle-bin restoration. Direct file-lifecycle targets at the two known loose `dlclist.xml` locations are rejected before writes. Whole-RPF payload replacements retain their existing behavior; this does not inspect or preserve individual files inside an archive. Schema v15 adds an append-only manual-registration ledger: intent is persisted before file changes and settlement is recorded with the successful metadata transaction. Settlement describes the file operation only. A failed or interrupted operation remains subject to manual review, including after a later successful operation. Database transactions do not guarantee filesystem rollback.

The Legacy SP and Legacy LSPDFR workspaces share reminders for the same game folder. The App displays the root, tracked owners and an XML entry to review; the CLI exposes `dlc-tasks` with the global `--game-path` filter. CLI operations and AI action results retain reminders and report lookup errors separately from operation errors. Current active and disabled owners are rechecked conservatively; shared, uncertain or unresolved work requires review. No completion button is provided in this phase.

The dedicated manual XML editor is described below; optional assistance through the existing Ollama Local, Ollama Cloud, Anthropic and OpenAI adapters remains planned separately. Users supply their own exported XML and use their existing archive tool to import edits; no RPF archive editor or base-game XML generator is implemented. Neither editing an exported XML file nor deploying a pack proves that the game has registered it.

Source-first regression coverage includes migration/reopening, XML preservation, both uninstall branches, restore, compound reinstallation, and database failures. The migration fixture covers the existing-table subset used by the test, not a complete historical database snapshot. The committed baseline received the remote validation described below; follow-up fixes require their own validation. The legacy automatic XML writer and its tests have been retired to match the manual-registration contract; this does not establish a passing release build.

### Dedicated DLC list editor: source implementation awaiting validation

<!-- OpenAI-Codex -->
Tools includes a separate DLC list editor for a valid user-exported XML file. It keeps an original snapshot and an editable draft, validates the current draft, and displays added/removed entry occurrences, duplicate entries and changes in the shared entry order. Nonstandard paths remain visible with warnings. Original and draft text remain available for review; the entry summary is not a complete text diff.

The supported form is UTF-8 XML 1.0, optionally with a BOM, within 5 MiB and 64 nested elements. It requires one `SMandatoryPacksData` root and one direct `Paths` child containing text-only `Item` entries; an empty Paths list is allowed with a warning. DTDs, custom entities, namespaces and unsupported Item content are rejected rather than partially interpreted. Validation does not certify that a game build will accept the file. The inspector requires a valid exported baseline; it is not an arbitrary malformed-XML repair tool.

Save as new XML revalidates the draft and source snapshot hash, then uses exclusive file creation and flushes the new output. Existing destinations, source aliases, protected paths, linked/reparse paths, Windows data-stream syntax and paths inside `update.rpf` are refused. No source truncation, archive import, automatic save or reminder completion occurs. A write/flush error retains any partial new file and reports its location. Path checks and file opening are separate operations, so they do not provide a handle-based filesystem transaction or eliminate concurrent ancestor/source replacement races.

Drafts are memory-only and survive switches between Tools tabs; save before leaving the Tools page. Opening another file requests confirmation for an unsaved draft. Editing invalidates the previous preview; stale validation replies are discarded, and errors retain the current draft. The original snapshot remains the baseline after saving a copy. No AI request is made in this phase. These editor sources and their new tests have not been compiled, executed or visually verified; the green `2972f6a` run applies only to the earlier baseline.

#### Optional AI draft assistance: source implementation awaiting validation

<!-- OpenAI-Codex -->
The next source phase adds an explicit request preview for Ollama Local, Ollama Cloud, Anthropic and OpenAI. Existing settings for other providers remain available to their existing features. The preview shows the fixed destination, model and complete system/user text. Preparing a preview does not connect to a provider or read its credential. Only explicit confirmation sends the XML and instruction; no source path, mod database, owner IDs or operation log is attached. The XML itself may contain private information. Cloud requests may incur charges.

The new request checks the current settings against the preview, then uses that immutable snapshot on a background worker without holding the database lock. It refuses redirects and has a 60-second timeout, with no automatic retry. UTF-8 byte limits are 64 KiB for input/output XML, 4 KiB for instructions and 1 MiB for the HTTP response body. Larger files remain eligible for manual editing within the existing 5 MiB limit. Provider token limits can still produce an unusable or truncated result; no successful suggestion is guaranteed.

Responses must be complete supported XML, with all bytes outside `Paths` and protected tags, attributes and non-Item tokens preserved. Invalid responses and Markdown wrappers are rejected without repair. An accepted suggestion is displayed separately; applying it changes only the in-memory draft and requires validation again before the existing save-as-new operation. Stale responses do not replace changed drafts. Leaving Tools discards pending UI results but does not cancel a request already sent. No automatic file write, RPF import, registration confirmation or reminder completion is performed.

The manual editor baseline `81c225d` passed remote Windows and Ubuntu CI. The new AI phase has source-first tests and static review only; it has not been compiled, tested against live providers, visually verified or accepted in-game. No local tests, builds, runner or workflow were executed for this phase.
